## Decisions Made During Build

- `create-next-app@latest` installs Next.js 16 by default. Pinned `package.json` to `next@^15` / `eslint-config-next@^15` (installed: 15.5.19) to match architecture.md.
- shadcn/ui init and `lib/utils.ts` (`cn()`) deferred to Phase 2 — not needed until the first UI primitive is built.
- Root project intentionally left outside git for now (create-next-app's nested git init was discarded during scaffold merge).
- Features 02 + 03 built together in one session — auth can't be verified without the DB existing, and the DB wiring can't be verified without auth working. `profiles`/`pitches` tables and RLS were applied manually in the Supabase dashboard beforehand (not via this session).
- Built minimal stub pages at `app/(app)/generate`, `/history`, `/profile` (+ pass-through `app/(app)/layout.tsx`, no Navbar yet) purely so the post-login middleware redirect could be verified in a browser. Real content for these routes lands in Features 06/09/10 — only the page body gets replaced, not the route.
- `signOut` server action lives in `actions/auth.ts` (not explicitly listed in architecture.md's tree, but follows its `actions/` convention). Temporarily wired to a plain button on the `/generate` stub via `<form action={signOut}>` until Feature 04 moves it into the real Navbar. Had to type `signOut` as `Promise<void>` (no `{success, error}` return) because Next.js form actions require a void-compatible return signature — returning an error object on the failure path broke the type contract with `<form action>`.
- Google OAuth required two manual dashboard steps outside the codebase: enabling the Google provider in Supabase (Authentication → Providers) and registering the exact Supabase callback URL (`https://<project-ref>.supabase.co/auth/v1/callback`) as an authorized redirect URI in Google Cloud Console. Both are one-time project config, not something future sessions need to repeat.
- `@supabase/supabase-js` logs a build warning about a Node.js API not supported in the Edge Runtime (used by `@supabase/ssr` inside `middleware.ts`). This is a known, harmless warning — build and runtime both work correctly despite it.
- Feature 04 (Navbar): the sign-out form moved from the `/generate` stub into `components/layout/Navbar.tsx`. Navbar is a Client Component (`usePathname` for active-link state); `app/(app)/layout.tsx` stays a Server Component and just renders `<Navbar />` above `{children}`, per code-standards.md's "never `use client` in layout files" rule. The `?error=signout_failed` banner stays on `/generate` since `signOut` always redirects failures there regardless of originating page.
- Feature 05 (Homepage): `app/page.tsx` checks auth server-side (same pattern as `/login`) and redirects logged-in users to `/generate` before rendering anything. Hero and "how it works" sections are inline in the page file (no extracted components, page-specific only) — reuses the existing Card token set for the 3 step cards. New `ui-registry.md` entries: Hero Section, Step Card.
- Feature 06 (Profile page): first form in the app. `app/(app)/profile/page.tsx` (Server Component) fetches the user's `profiles` row server-side and passes it as `initialData` into `components/profile/ProfileForm.tsx` (Client Component) — the client form never touches the DB directly. `actions/profile.ts`'s `saveProfile` **upserts** on `user_id` (`onConflict: "user_id"`) since there's no DB trigger creating a profile row on signup — this means the same action works for both brand-new and returning users without a separate "create profile" step. Tone field uses a plain native `<select>` styled with the same token classes as text inputs, not a shadcn primitive — first time the "approved dependencies" check (shadcn? native Next.js? simpler native solution?) favored the native solution. Validation in `saveProfile` is manual (`if` checks), not zod — zod stays uninstalled; first real validation need that arises with more complex input (e.g. Feature 09's generate action) should revisit whether zod is worth pulling in then. Added a new `types/index.ts` file with `Profile` and `Tone` types — first file in `types/`.
- Features 07 + 08 + 09 built together in one session (per `/architect`) since the fetcher and Gemini integration have no way to verify they work without the generate page wiring them together. `npm install cheerio @google/generative-ai` — first installs since project scaffold. `lib/fetcher.ts`'s `fetchWebsiteText` normalizes the URL (prepends `https://` if no scheme), uses a 10s `AbortController` timeout + a real `User-Agent` header (some sites block the default fetch UA), and rejects non-2xx/non-`text/html` responses before handing HTML to cheerio — none of this HTTP-level robustness was in library-docs.md's cheerio snippet, which only covered the parsing half. `lib/gemini.ts`'s prompt explicitly bans bracket placeholders (`[Company Name]`, `[Your Name]`, etc.) and instructs Gemini to use the real company name from the site content, falling back to the URL's domain (via `lib/fetcher.ts`'s `extractDomain`) if the name can't be determined. `app/api/generate/route.ts` does its own `auth.getUser()` check and 401s if missing — `middleware.ts`'s matcher checks `pathname.startsWith("/generate")`, which `"/api/generate"` does not satisfy, so API routes are **not** covered by the existing middleware protection. Regenerate re-runs the entire pipeline (re-fetch + re-call Gemini) through the exact same endpoint and request body as the initial generate — every call, including regenerates, inserts a new immutable `pitches` row; there is no "skip fetch, reuse content" mode. `prospect_summary` is the first ~300 chars of the cleaned site text (word-boundary trimmed), not a second Gemini call — architecture.md describes `lib/gemini.ts` as writing the email only. `PitchOutput` is rendered conditionally inside `PitchForm` (which owns all url/result/loading/error state) rather than introducing a third wrapper component, mirroring the Feature 06 server-page + single-client-component pattern. Validation stayed manual (no zod) — one URL field still isn't complex enough to justify it; revisit if a future feature needs more than that.
- First live test of Feature 09 failed with a 502 (`[api/generate] gemini failed`) on every request — root cause was `"gemini-1.5-flash"` itself, not the integration code: Google retired the entire Gemini 1.5 line, so every `generateContent` call 404'd. Confirmed via a standalone script hitting `ListModels` directly. Switched `lib/gemini.ts` to `"gemini-2.5-flash"` (current stable fast model) and verified a real call succeeds. `library-docs.md` updated with the new model name and a note to re-run `ListModels` if this happens again — its model recommendations can go stale since they're a point-in-time snapshot, not a live source of truth.
- `/review` on Features 07–09 found 6 issues, all fixed: (1) `PitchForm.tsx`'s Regenerate now re-submits `pitch.prospect_url` instead of the live URL input — previously, editing the input after a successful generate without resubmitting would silently regenerate a different prospect under the "Regenerate" label. (2) The URL input is now `disabled` while a request is in flight. (3) `lib/fetcher.ts` had no SSRF protection — `fetchWebsiteText` now resolves the hostname via `dns.lookup` and rejects loopback/private/link-local addresses (covers cloud metadata endpoints), and switched to `redirect: "manual"` so a 3xx response can't bypass the host check; no new dependency needed, Node's built-in `dns` module is enough. (4) `app/api/generate/route.ts`'s `const body = await req.json()` was an implicit `any` — added a `parseUrl(body: unknown)` helper that narrows properly, one justified `as { url: unknown }` cast with a comment per code-standards.md's exception clause. (5) `architecture.md`'s boundary table said AI calls live "in `app/api/generate/route.ts` only" and listed `lib` under "Never in" — contradicted its own Folder Structure section, which defines `lib/gemini.ts` as the Gemini wrapper. Reworded to `lib/gemini.ts` + API route, matching the `lib/fetcher.ts` row's phrasing. (6) `app/(app)/generate/page.tsx` now does its own `auth.getUser()` + redirect, matching the Profile/Homepage pattern, instead of relying solely on `middleware.ts`.
- Separately tuned `lib/gemini.ts`'s prompt only (no other files touched, by request): emails are now capped at 80 words and structured as exactly three sentences (specific observation about the prospect → connects it to the sender's services → call to action) plus a sign-off, with an explicit instruction not to spend more than one sentence on the sender's own background.
- Feature 10 (Pitch history) built per `/architect`. `ui-rules.md`'s Do Nots gained one exception (`position: fixed` permitted for modal overlays only) to unblock a real modal — first conflict between an existing rule and a new feature's needs. Modal + delete-confirmation both use shadcn/ui Dialog, first shadcn install in the project: `npx shadcn init` was far more invasive than expected, overwriting `app/layout.tsx` (Inter → Geist) and injecting a competing oklch theme into `app/globals.css` — both restored, and the generated `components/ui/dialog.tsx` was fully rewritten to use only this project's tokens (no shadcn default classes remain). Correction for the record: this shadcn version builds Dialog on `@base-ui/react`, **not Radix** — `code-standards.md`'s Approved Dependencies list updated accordingly (`@base-ui/react`, `clsx`, `tailwind-merge`, `tw-animate-css`; `shadcn` itself moved to devDependencies as a codegen-only tool). Unused `components/ui/button.tsx` and `class-variance-authority` (its only consumer) were removed since `DialogFooter` takes plain buttons from each caller instead of a shared `<Button>`. `actions/pitches.ts`'s `deletePitch` enforces ownership at the DB level (`.eq("id", id).eq("user_id", user.id)` in the delete query itself, not a fetch-then-check) per explicit instruction. `/review` found 4 issues, all fixed: an unjustified `as Pitch[]` cast in `app/(app)/history/page.tsx` (removed — `tsc` stayed clean without it); a keyboard-only bug where Enter/Space on the row's Delete button bubbled to the row's own `onKeyDown` and opened the detail dialog too (fixed with `stopPropagation` on the button's `onKeyDown`, mirroring its `onClick`); a silent error/empty-state conflation where a failed Supabase fetch rendered the cheerful "no pitches yet" empty state instead of an error banner (fixed); and the detail dialog rendering an empty `<p>` for falsy `email_content` instead of following Pitch Output's fail-safe-empty precedent (fixed with a muted fallback message — the row itself stays visible/deletable, unlike Pitch Output which returns `null` entirely, since this is saved history rather than an in-flight result). New `ui-registry.md` entries: Dialog (Modal Overlay & Content Shell), Pitch History Row, Pitch History List.

- Visual polish (not in build-plan.md, added by explicit request this session): Navbar swapped `bg-surface` for `backdrop-blur-md bg-white/80` (frosted glass over scrolled content). Homepage hero headline got a gradient-text treatment (`bg-gradient-to-r from-accent to-accent-hover bg-clip-text text-transparent`) plus two blurred background orbs — the orbs required the hero `<section>` to be `relative overflow-hidden` (containment on narrow screens) with the actual heading/subhead/CTA wrapped in their own `relative z-10` div, because plain static content paints *before* `z-index: 0` positioned siblings in CSS stacking order and would otherwise render underneath the orbs, not above them. Card hover lift (`hover:shadow-md hover:border-border-strong transition-all duration-200`) was deliberately scoped to cards in an interactive flow or repeated grid — Step Cards and the Pitch Output card — and explicitly excluded from one-off static shells (Auth Card, Profile Form's wrapping card); each interactive card carries an inline "interactive card — hover lift intentional" comment. The Generate button alone got an indigo glow-on-hover (`hover:shadow-[0_0_20px_rgba(91,78,232,0.4)]`) — not applied to Regenerate or any other Primary button. A full `transition-colors` audit (`grep -rn "transition-colors" | grep -v duration`) found and fixed three places missing an explicit duration (`Navbar.tsx`'s nav links and sign-out button, `PitchHistoryRow.tsx`'s row and Delete button, `dialog.tsx`'s close button) — all now `duration-150`, matching the app-wide standard. Copy button's "Copied!" label also changed to "Copied ✓" per this session's explicit request.
